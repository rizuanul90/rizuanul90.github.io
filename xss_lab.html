// Overview

What Is Cross-Site Scripting?

Cross-Site Scripting (XSS) is a web vulnerability where an attacker injects malicious scripts into content that other users' browsers will render. It happens when an application takes untrusted input and includes it in the HTML response without proper validation or output encoding. Reflected XSS — the type covered in this lab — is non-persistent: the payload travels in a URL and executes the moment a victim opens that link.

Burp Suite CommunityIntercept, inspect, and modify HTTP requests before they reach the server

// WHY THIS MATTERS XSS sits in the OWASP Top 10 and remains one of the most common web app vulnerabilities. A successful exploit can steal session cookies, hijack accounts, or redirect users to phishing pages — all from a single malicious link. This lab focuses on understanding *why* each context behaves differently, since that's the foundation for writing effective input validation and output encoding rules.

Burp Suite & Proxy Setup
Launch Burp Suite, install FoxyProxy in Firefox, and import Burp's CA certificate so HTTPS traffic can be intercepted and decrypted.
Step 01Launch Burp Suite on Kali Linux
Open the Kali application menu and search for Burpsuite. Click the dragon icon to launch.
If a JRE compatibility warning appears, check "Don't show again" and click OK. On the Terms & Conditions screen, click the orange I Accept button. When prompted, select Temporary project and click Next, then leave the configuration as Burp defaults and click Start Burp.
Step 02Install FoxyProxy in Firefox
Open Firefox in the Kali VM and search for FoxyProxy Basic. Click the Mozilla Add-ons result, click Add to Firefox, and confirm the install prompt.
Click the fox icon in the toolbar → Options → Add, and configure a new proxy entry pointing at Burp's default listener:
foxyproxy config
# Title             Burp
# Proxy Type        HTTP
# Proxy IP Address  127.0.0.1
# Port              8080
Click Save, then click the fox icon again and select Burp to route all traffic through the proxy.
Step 03Import Burp's CA Certificate
With FoxyProxy set to Burp, browse to http://burpsuite, then click CA Certificate in the top right to download cacert.der.
In Firefox, open the menu (☰) → Settings → search certificate → View Certificates → Import. Select the downloaded file, check both trust boxes, and click OK.
// WHY IMPORT THE CA CERTIFICATE? Burp generates its own TLS certificates on the fly to sit between the browser and the target server. Without trusting Burp's CA, Firefox rejects every HTTPS connection that passes through the proxy — importing the PortSwigger CA lets Firefox accept those certificates so encrypted traffic can still be inspected.

// Part 2 of 4
Reflected XSS — Body Parameter
The simplest injection context: the parameter value is reflected straight into the HTML <body> with no encoding, so a raw <script> tag executes as-is.
Step 04Open Reflected XSS → Parameter – Body
Navigate to https://public-firing-range.appspot.com and click Reflected XSS. In Burp, go to Proxy → Intercept and click Intercept is on. Back in the browser, click Parameter – Body.
Step 05Send the Intercepted Request to Repeater
Burp pauses the request — a GET to /reflected/parameter/body?q=a. Right-click it and select Send to Repeater (Ctrl+R), then switch to the Repeater tab and click Send.
response (excerpt)
<html>
  <body>
    a
  </body>
</html>
The value a from the q parameter lands directly inside the <body> with zero encoding.
Step 06Inject the Script Payload
In the Repeater request, replace a with a script tag and resend:
modified request
GET /reflected/parameter/body?q=<script>alert(1)</script> HTTP/2
The response now reflects the script tag unescaped inside the body. Right-click the response → Copy URL, return to Proxy and turn off intercept, then paste the URL into a new tab.
// XSS CONFIRMED — BODY PARAMETER The browser parses and executes the injected <script> tag, popping an alert. In a real attack, this payload would be swapped for cookie exfiltration, a credential-harvesting redirect, or a beacon to an attacker-controlled server.

// Part 3 of 4
Reflected XSS — Title Tag Context
When input lands inside an existing tag like <title>, a bare <script> injection is treated as plain text. The tag has to be closed first before the script can execute.
Step 07Intercept the Title Parameter
Re-enable intercept in Burp, then click Parameter – Title on the Reflected XSS page. Send the request to Repeater and click Send.
response (excerpt)
<head>
  <title>
    a
  </title>
</head>
This time the value sits inside <title>. Injecting <script>alert(1)</script> directly here would just become text content of the title — it won't execute.
Step 08Close the Title Tag Before Injecting
Replace a with a payload that first closes </title> before adding the script:
modified request
GET /reflected/parameter/title?q=</title><script>alert(1)</script> HTTP/2
Send it, copy the URL, turn off intercept, and open the URL in a new tab — the alert fires, confirming the title context was successfully escaped.
// CONTEXT MATTERS The same payload doesn't work everywhere. A payload that succeeds inside a body parameter can fail silently inside a title, an HTML attribute, or a script block. Knowing exactly where the input lands in the response is the difference between a working exploit and a dead end.

HTML Comment & Tag-Based Filter Bypass
Two more contexts: breaking out of an HTML comment, and getting around a tag-based input filter using an SVG element with an inline event handler.

HTML Comment Context

Step 09Escape the HTML Comment
On the Reflected XSS page, intercept Parameter – Body HTML comment. Send to Repeater and click Send.
response (excerpt)
<body>
  <!-- a -->
</body>
Anything inside <!-- --> is ignored by the browser. To break out, close the comment with --> before the script:
modified request
GET /tags/multiline?q=--><script>alert(1)</script> HTTP/2
Send, copy the URL, turn off intercept, and paste into a new tab — the comment is closed, the script runs, and the alert pops.

Tag-Based Filter Bypass

Step 10Trigger the Tag Filter
Return to the Firing Range home page, click Tag Based XSS, turn intercept on, and click Multiline Tag. Send the request to Repeater and click Send — the response looks similar to the body parameter case from Part 2.
Try replacing a with <script>alert(1)</script> and send — this time the server returns a 400.
error response
HTTP/2 400 Bad Request
<h1>Error: Invalid input, contains tags.</h1>
Step 11Bypass with an SVG Event Handler
The filter blocks complete <tag> patterns but doesn't catch a lone opening <. An SVG element with an inline onload handler doesn't need the same closing structure — using %20 (URL-encoded space) keeps it from matching the filter's pattern:
filter bypass payload
GET /tags/multiline?q=<svg/onload=alert(1)%20 HTTP/2
Send the request — it returns 200 OK, with the SVG and its onload handler intact in the response body. Copy the URL, disable intercept, and open it in a new tab — the alert fires.
// INCOMPLETE FILTERING IS DANGEROUS The server blocked <tag> patterns but forgot standalone < characters. Blocklist-based filters fail like this constantly — there are too many ways to construct an XSS payload to enumerate them all. The fix isn't a smarter blocklist; it's HTML entity-encoding all user-supplied output at the point it's rendered, regardless of what characters it contains.
// Summary

Lab Summary

This lab walked through discovering and exploiting Reflected XSS across four different HTML injection contexts using Burp Suite as an intercepting proxy. Each context required a different payload — proof that effective XSS testing (and defense) depends on understanding exactly where untrusted input lands in the rendered HTML.

ContextPayloadWhy It Works
Body Parameter<script>alert(1)</script>Reflected directly into the body — no encoding, no context to escape
Title Tag</title><script>alert(1)</script>Must close <title> first to reach an executable script context
HTML Comment--><script>alert(1)</script>Must close the comment block before the script tag is parsed as HTML
Tag Filter Bypass<svg/onload=alert(1)%20Filter blocked full <tag> pairs but missed a lone opening <

// Defensive Takeaways

  • Output encodingConvert <, >, &, ", and ' to their HTML entity equivalents before rendering any user-supplied data
  • Context-aware encodingApply different encoding rules depending on whether output lands in HTML body, an attribute, or a script block
  • Avoid blocklistsPattern-matching against "known bad" tags is brittle — the SVG bypass shows how easily it's defeated
  • Content Security PolicyA strict CSP blocks inline script execution even if encoding fails somewhere
